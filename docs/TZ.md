Техническое задание на разработку системы учёта заявок

Проект: RequestSystem Исполнитель: Замятин Константин Дмитриевич Группа: еозИСИП-308 Дата: 05.11.2026

1. Назначение

Система предназначена для автоматизации процесса обработки обращений в учебном заведении или небольшом отделе.
Без системы заявки передаются устно, через электронную почту или мессенджеры, что приводит к потере информации, отсутствию контроля сроков, качества и невозможности собрать статистику.
Программа решает проблему прозрачности: каждое обращение регистрируется, имеет ответственного исполнителя и отслеживаемый статус и историю, исключает потерю заявок и снижает риски необработки (несвоевременной обработки) обращений, позволяет производить анализ качества, количества и скорости обработки обращений.

2. Роли пользователей и их права

Заявитель (Автор заявки): любой сотрудник или студент.
Создание новой заявки.
Просмотр списка своих заявок.
Добавление комментариев к своим заявкам.
Просмотр истории изменений своей заявки.
Оценка качества выполненной работы.
Возврат заявки в работу (на этапе приёмки).

Исполнитель: сотрудник технической поддержки или ответственный специалист.
Просмотр списка заявок, назначенных на него.
Изменение статуса заявки (принять в работу, отметить выполненной).
Добавление комментариев.
Редактирование описания заявки (только до момента первого перевода из статуса «Новая»).

Оператор (Диспетчер): сотрудник, координирующий поток заявок.
Просмотр всех заявок в системе.
Назначение исполнителя на заявку.
Изменение статуса заявки (например, перевод из «Новой» в «В работе»).
Категоризация заявок.
Изменение категории заявки.
Экспорт списка заявок в формат CSV.

Администратор: системный управляющий.
Полный доступ ко всем данным с правом редактирования, но с соблюдением системных ограничений (запрет на безвозвратное удаление заявок, только архивация).
Управление справочниками (создание и удаление категорий).
Управление учетными записями пользователей (создание, блокировка).
Просмотр системных логов.
Просмотр всех заявок (с правами Оператора).

3. Функциональные требования (Система должна…)
Обеспечивать регистрацию новой заявки с автоматическим присвоением уникального номера в формате #YYYY-NNNN.
Хранить историю всех изменений статуса и исполнителя в карточке заявки (Audit Log).
Позволять фильтровать и сортировать список заявок по статусу, категории, исполнителю и дате.
Автоматически отправлять уведомление заявителю при смене статуса его заявки.
Реализовывать ролевую модель доступа (RBAC), ограничивая действия пользователя его правами.
Вести справочник категорий (иерархический, с parent_id) с возможностью добавления новых элементов администратором.
Предоставлять форму поиска заявок по ключевым словам в теме или описании.
Блокировать удаление заявок, разрешая только их закрытие (архивацию).
Отображать на главной панели оператора количество заявок в статусах «Новая» и «В работе».
Экспортировать список заявок в формат CSV для последующей аналитики.
Реализовать прикрепление файлов (скриншотов, документов) к заявке или комментарию.

4. Нефункциональные требования
Удобство (Usability): интерфейс должен быть интуитивно понятным, время на регистрацию заявки не должно превышать 2 минут для неавторизованного пользователя. Основные действия (создание, смена статуса) доступны в 1–2 клика.
Надёжность (Reliability): доступность системы 99% времени (учебное время), время восстановления после сбоя не более 30 минут. Система не должна терять данные при внезапном отключении питания.
Производительность (Performance): время отклика интерфейса при загрузке списка из 100 заявок не должно превышать 2 секунд. Время сохранения новой заявки — не более 1 секунды.
Безопасность (Security): хранение паролей в виде хешей (например, bcrypt), защита от SQL-инъекций и XSS-атак, передача данных по зашифрованному каналу (HTTPS).
Сопровождаемость (Maintainability): код должен быть покрыт комментариями, структура проекта должна соответствовать выбранному фреймворку, наличие файла README с инструкцией по развертыванию.

5. Сценарии использования (Use Case)
Регистрация обращения: Заявитель заходит в систему, нажимает «Создать заявку», заполняет тему и описание, выбирает категорию, прикрепляет файл. Система сохраняет заявку со статусом «Новая».
Назначение исполнителя: Оператор открывает список новых заявок, выбирает свободную, нажимает «Назначить» и выбирает Исполнителя из списка (в списке отображаются только пользователи с ролью «Исполнитель»). Статус меняется на «В работе».
Выполнение работ: Исполнитель выполняет задачу, добавляет комментарий с результатом и переводит статус в «Выполнена».
Приёмка результата: Заявитель получает уведомление, проверяет результат в интерфейсе и переводит статус в «Закрыта». Если результат не устраивает, Заявитель нажимает «Вернуть в работу», указывает причину, и заявка переходит в статус «В работе» с уведомлением Исполнителя.
Администрирование: Администратор заходит в раздел «Справочники», добавляет новую категорию «Проблемы с принтером», и она сразу становится доступной всем пользователям при создании заявки.

Преподаватель подтвердит выполнение работы, если:

Создана верная папочная структура (docs, src, tests) и в docs лежит заполненный файл TZ.md.
В ТЗ присутствуют все 6 обязательных разделов с соблюдением указанных минимумов.
Описанные роли не имеют логических пересечений прав.
При нажатии кнопки «Назначить» в списке отображаются только те пользователи, у которых роль «Исполнитель».
Созданная заявка получает уникальный номер в формате #YYYY-NNNN.
Функциональные требования описывают конкретные действия системы.
Нефункциональные требования охватывают все пять аспектов (UX, надежность, скорость, защита, код).
Сущности логически связаны между собой.
В файле TZ.md присутствует диаграмма Use Case в виде Mermaid-синтаксиса.

Статус: id, название (Новая, В работе, Выполнена, Закрыта).
Категория: id, parent_id, название.
Комментарий: id, текст, дата, author_id, ticket_id.
Вложение (Attachment): id, имя_файла, mime_тип, размер, путь_к_хранилищу, ticket_id.
Уведомление (Notification): id, user_id, тип, тема, текст, статус отправки, ticket_id.
История изменений (Audit Log): id, ticket_id, user_id, action_type, old_value, new_value, timestamp.
